# CampusFlow deployment: GitHub → Render (Docker + persistent SQLite)

> **Not deployed automatically.** You must connect your own GitHub and Render accounts and explicitly agree to any hosting charges. Render persistent disks require a paid service and are unavailable on a free web service. Read the current provider pricing before creating one.

## Why one service?

The Dockerfile builds the React/Vite frontend and serves its `dist/` files from the FastAPI backend. Both frontend and API use the same origin, such as `https://your-app.onrender.com/`, so there is no separate Vercel site, CORS configuration, or local development proxy in production.

Local development **still uses two terminals** and the Vite proxy. The output file `frontend/dist/` is generated by `npm run build` and is never committed.

## 1. Final local checks

From `campusflow/backend`:

```powershell
python -m pip install -r requirements-dev.txt
python -m pytest -q
```

From `campusflow/frontend`:

```powershell
npm install
npm run build
```

The Python tests run here, but the React build must also succeed on your computer or GitHub Actions before deployment.

## 2. Prepare a public-safe repository

The Git repository root must contain:

```text
.github/workflows/campusflow-ci.yml
README.md
render.yaml
campusflow/
  Dockerfile
  backend/
  frontend/
  DEPLOYMENT.md
```

Check staged files before committing. Never commit `students.db`, CSV/Excel student exports, secrets, or account credentials. The provided `.gitignore` and `.dockerignore` block these common files; **check `git diff --cached --name-only` as well**. If any private data was previously committed, ignoring it now does not remove it from Git history; rotate affected credentials and clean the history before publishing.

## 3. Create an isolated **fictional data only** public demo

Your local Phase 13 database, student records, and admin login do **not** need to be uploaded. The cloud version will create a *separate* database on its persistent disk.

This demo is opt-in and runs **only if** `CAMPUSFLOW_BOOTSTRAP_DEMO=1`. At first startup, only when there are **no users and no students**, it will create:

- 24 *fictional* students with `example.com` email addresses,
- fictional grades and attendance,
- one private administrator,
- one visitor with an underlying teacher role but enforced **read-only** permissions.

Never publicize the administrator credentials. The viewer may read fictional records but cannot add/change marks, attendance, student details, events, or accounts.

## 4. Configure Render Blueprint

1. Push the production-ready repository to GitHub and check that the GitHub Actions workflow is green.
2. Sign in to [Render](https://dashboard.render.com/) and create a **new Blueprint** from your GitHub repository. Render reads the repository-root `render.yaml`.
3. Review the selected **paid plan** and persistent-disk charges before approving deployment. `render.yaml` specifies a paid Starter service and a 1 GB disk mounted at `/data`. Increase RAM if needed for Python/scikit-learn dependencies.
4. Enter **private** values for the prompted environment variables:

   | Setting | Value |
   | --- | --- |
   | `CAMPUSFLOW_BOOTSTRAP_DEMO` | `1` (from blueprint) |
   | `CAMPUSFLOW_ADMIN_USERNAME` | Your private admin username (e.g. `portfolioadmin`) |
   | `CAMPUSFLOW_ADMIN_PASSWORD` | A unique secret, 12–128 characters |
   | `CAMPUSFLOW_PUBLIC_VIEWER_USERNAME` | `demo` (from blueprint) |
   | `CAMPUSFLOW_VIEWER_PASSWORD` | A separate unique 12–128-character password; share only for fictional demo |
   | `STUDENTS_DB` | `/data/students.db` (from blueprint) |

5. Allow the first deployment to build. The Docker startup bootstraps the empty demo database before starting FastAPI. Password values are **never** printed by the setup code. Future restarts skip bootstrapping when any users/students already exist.
6. Open the deployed app's `onrender.com` URL and test login as both admin and demo viewer. Only share the **viewer** credentials with recruiters.

**If you already have a Render service/database:** do not enable demo bootstrapping on it. Create a new service with a separate empty disk, not an existing university database.

**Note on persistence:** Render disks persist only files inside the mounted path and are accessible by a single service instance. This blueprint deliberately uses one instance. Backup is still necessary; snapshots are not a replacement for deliberate disaster recovery procedures.

## 5. Smoke test the deployed URL

From anywhere with Python:

```powershell
python campusflow/scripts/smoke_check.py https://YOUR-APP.onrender.com
```

Checks API health, release information, authentication protection, the frontend page, and unknown API routes. This script **does not** perform an authenticated end-to-end browser test or change records.

Next, complete the interactive [QA checklist](docs/QA_CHECKLIST.md). Test the public demo with the **demo viewer**, and check marks/attendance changes only with the private admin on fictional data.

## 6. Troubleshooting

- **502 / health failure:** Review Render logs. `/api/health` opens the SQLite file; the persistent disk must be mounted and writable at `/data`.
- **No login:** Check that demo bootstrap variables were provided and the database was empty. Never run bootstrap against an existing populated database.
- **Blank page:** Check GitHub Actions React build logs, browser developer console, and Docker build logs for Vite errors.
- **Read-only demo can edit:** Verify `CAMPUSFLOW_PUBLIC_VIEWER_USERNAME` exactly matches the public viewer account and redeploy. Do not share credentials if that check fails.
- **Data disappears after restart:** Verify the disk is attached at `/data` and `STUDENTS_DB=/data/students.db`. A service without a persistent disk is not acceptable for this deployment.
- **Out of memory:** Adjust Render's paid instance size; scikit-learn, numpy, and ReportLab increase memory use.

## Security and scale limitations

This is a **portfolio demo**, not an audited academic records system. Do not host real student data without further security, privacy, backup, monitoring, and operational reviews. SQLite with one mounted disk is not suitable for horizontal scaling or a production university deployment; a future PostgreSQL migration would be more appropriate.
